# Feature Specification: 傳遞依賴破壞性變更閘門

**Feature Branch**: `build/dep-breaking-change-gate`

**Created**: 2026-08-01

**Status**: Draft

**Input**: User description:

> 在 CI 加入「傳遞依賴破壞性變更」閘門。
>
> 背景與動機：本 repo 的兩個 starter 都以 `api` scope 曝露核心依賴（knolux-redis → `spring-boot-starter-data-redis`；knolux-s3 → `software.amazon.awssdk:s3`），因此傳遞依賴的 major 版本變動，等同於對下游消費者的破壞性變更——即使本專案自有原始碼一行都沒改。目前沒有任何自動化機制能攔截這種情形。
>
> 具體失效案例：2026-08-01 發布的 redis 1.4.0，在自有原始碼零變更（`v1.3.0..main` 的 `.java` diff 為空）的情況下，因升級 Spring Boot 4.0.6 → 4.1.0 而把 `io.lettuce:lettuce-core` 從 6.8.2.RELEASE 帶到 7.5.2.RELEASE（跨 major），並讓 `io.netty` 的 4.1.x 線整個消失。此事直到發布後才由人工比對完整依賴樹發現，當時版號已推上 GitHub Packages 無法回收，只能事後在 Release notes 與 CHANGELOG 補揭露。
>
> 需要解決的問題：讓同類變更在「合併前」而非「發布後」被攔截，且攔截結果要能直接用於撰寫 CHANGELOG 與 Release notes 的升級揭露。
>
> 期望行為要點：針對兩個模組比對「前一個已發布 tag」與當前 HEAD 之間會外溢給下游的 resolved 依賴版本；偵測 major 版本跳動、依賴新增、依賴移除三類變化；出現 major 跳動或依賴移除時 CI 必須失敗並清楚指出模組、依賴、版本區間；minor / patch 變動不阻擋建置僅列入報告；產出的差異報告需人類可讀且適合直接貼進 CHANGELOG 的「升級前必讀」段落。
>
> 限制條件：本 repo 刻意維持輕量工具鏈（無 checkstyle / spotless），不應引入沉重外掛或大量設定；不採用 Gradle 內建 dependency locking；不採用 japicmp。

**對上述失效案例的事後更正（2026-08-02，由 T051 的實測推翻）**：以本功能的工具重建 `knolux-redis-spring-boot-starter/v1.3.0` 的基準線後比對發現，redis 1.4.0 的外溢依賴**只有** Lettuce 6.8.2.RELEASE → 7.5.2.RELEASE 一項跨 major 變更；`io.netty` 的 4.1.x **從未出現在 v1.3.0 的 `runtimeClasspath` 上**（該版已全數解析為 `4.2.12.Final`），因此並不存在「4.1.x 線整個消失」的移除事件。誤判來源是 `./gradlew dependencies` 輸出中括號內的 *requested* 版本（`lettuce-core:6.8.2.RELEASE` 確實 requested `netty:4.1.125.Final`，但被 Spring Boot BOM 規則選為 `4.2.12.Final`）被當成了解析結果。

此更正不改變本功能的動機，反而強化它：**人工比對依賴樹除了會漏看，也會看錯**，而兩種錯誤方向都只有在讀「解析後的實際結果」時才能避免。`CHANGELOG.md` 的對應揭露已同步更正。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 合併前攔截破壞性依賴變更 (Priority: P1)

維護者（或 Dependabot）提出一個變更集。CI 自動判定每個模組「會外溢給下游」的依賴集合，與該模組最近一次已發布版本比對。若某依賴跨了 major 版本，或某依賴從集合中消失，建置立即失敗，並指出是哪個模組的哪個依賴、從哪一版變成哪一版、屬於哪一類變更。

**Why this priority**: 這是整個功能存在的唯一理由。沒有它，2026-08-01 的 redis 1.4.0 事件會重演——自有原始碼零變更卻對下游造成破壞性變更，且直到版號無法回收後才被發現。其餘故事都是在此基礎上提升可用性。

**Independent Test**: 建立一個刻意讓某依賴跨 major 的分支（例如單獨升級 Spring Boot 或 AWS SDK 的 major 版本），提出 PR，驗證建置失敗且失敗訊息含該依賴的座標與前後版本。此故事單獨實作即可交付核心價值。

**Acceptance Scenarios**:

1. **Given** `knolux-redis-spring-boot-starter` 最近發布版本的外溢依賴含 `io.lettuce:lettuce-core:6.8.2.RELEASE`，**When** 變更集使其解析為 `7.5.2.RELEASE`，**Then** 建置失敗，訊息指出模組為 `knolux-redis-spring-boot-starter`、依賴為 `io.lettuce:lettuce-core`、`6.8.2.RELEASE → 7.5.2.RELEASE`、類別為 major 版本跳動
2. **Given** 基準線的外溢依賴含某個座標（例如 `io.netty:netty-transport`），**When** 變更集使該座標完全不再出現於外溢依賴集合，**Then** 建置失敗，訊息指出該依賴被移除及其基準線版本
3. **Given** 一個變更集同時觸發上述兩種情形，**When** 閘門執行，**Then** 兩項皆完整列出，不因先遇到其中一項就中止
4. **Given** 一個變更集同時影響兩個模組，**When** 閘門執行，**Then** 兩個模組的判定結果皆呈現，並各自標明模組歸屬
5. **Given** 變更集僅修改文件（README、CHANGELOG）而未動依賴，**When** 閘門執行，**Then** 建置通過且報告顯示無依賴變動

---

### User Story 2 - 產出可直接引用的升級揭露報告 (Priority: P2)

發版者在撰寫 CHANGELOG 的「升級前必讀」段落與 GitHub Release notes 時，直接取用閘門產出的依賴差異報告，不需自行比對依賴樹。報告涵蓋所有類別的變動（包含不阻擋建置的 minor / patch 與新增），並明確區分「阻擋性」與「資訊性」。

**Why this priority**: 攔截只解決一半問題；另一半是「發版時該揭露什麼」。redis 1.4.0 的事後補救工作——手動比對 51 與 68 條依賴、手寫變更表格——正是缺少此項的成本。此故事可獨立於 P1 的阻擋行為存在（先只產報告不阻擋亦有價值）。

**Independent Test**: 在一個已知含依賴變動的分支上執行閘門，檢查報告是否包含模組名、依賴座標、基準線版本、當前版本、變更分類，且格式可直接貼入 Markdown 文件而不需重新排版。

**Acceptance Scenarios**:

1. **Given** 一個含 major、minor、patch、新增、移除各類變動的變更集，**When** 閘門執行，**Then** 報告完整列出所有類別，且阻擋性與資訊性變動在視覺上可區分
2. **Given** 閘門判定為失敗，**When** 建置結束，**Then** 報告仍然產出，不因失敗而遺失
3. **Given** 閘門判定為通過，**When** 建置結束，**Then** 報告仍然產出
4. **Given** 報告已產出，**When** 發版者將其貼入 CHANGELOG 的「升級前必讀」段落，**Then** 不需手動改寫格式即可閱讀

---

### User Story 3 - 不阻擋日常的 minor / patch 更新 (Priority: P3)

Dependabot 每週提出的依賴更新 PR，若解析後的外溢依賴僅有 minor 或 patch 變動、或僅新增依賴，建置照常通過，變動僅出現在報告中供審查者參考。

**Why this priority**: 這決定閘門是「能長期存活」還是「三週後被停用」。若每支 bot PR 都紅燈，維護者會關掉閘門，前兩個故事的價值隨之歸零。但在只有少量 PR 的階段，即使暫時過度阻擋也不致命，故列為 P3。

**Independent Test**: 建立一個僅升級某依賴 patch 版本的分支，驗證建置綠燈通過，且報告中列出該變動並標示為資訊性。

**Acceptance Scenarios**:

1. **Given** 變更集僅使某外溢依賴的 patch 版本前進，**When** 閘門執行，**Then** 建置通過且報告將其標示為資訊性變動
2. **Given** 變更集僅使某外溢依賴的 minor 版本前進，**When** 閘門執行，**Then** 建置通過
3. **Given** 變更集僅新增一個外溢依賴而未移除或跨 major，**When** 閘門執行，**Then** 建置通過且報告列出該新增

---

### User Story 4 - 核准有意為之的破壞性變更 (Priority: P2)

當維護者確認某項破壞性依賴變更是刻意且已評估過的（例如隨 Spring Boot major 升級而必然發生），能以明確、留下可審計紀錄的方式核准該變更，讓建置通過並繼續合併流程。

**Why this priority**: 沒有核准途徑的閘門會讓刻意的 major 升級永遠無法合併，屆時唯一出路是停用閘門——等同於功能不存在。此故事與 P1 同等關鍵，但依賴 P1 先存在才有意義，故並列 P2。

**Independent Test**: 對一個已被閘門阻擋的變更集執行核准動作，驗證建置轉為通過，且核准的內容（哪個模組、哪個依賴、哪個版本區間被核准）可事後查閱。

**Acceptance Scenarios**:

1. **Given** 某變更集因 major 跳動被阻擋，**When** 維護者核准該項特定變更，**Then** 建置通過
2. **Given** 已核准 `io.lettuce:lettuce-core` 的 6.x → 7.x，**When** 同一變更集又出現另一項未核准的破壞性變更，**Then** 建置仍失敗並僅指出未核准的那一項
3. **Given** 某破壞性變更已被核准，**When** 事後審查該變更集，**Then** 可查得核准了什麼、涵蓋哪個版本區間
4. **Given** 某項核准對應的依賴變更已隨發版完成並成為新基準線，**When** 後續變更集執行閘門，**Then** 該項核准不再影響判定

---

### Edge Cases

- **模組尚無任何已發布版本**（首次發布）：沒有基準線可比對。閘門不得失敗，也不得靜默通過——必須在報告中明確記錄「該模組因無基準線而跳過」。
- **版本字串不符合純語意化版本**：本專案的真實依賴含 `6.8.2.RELEASE`（Lettuce）、`4.1.136.Final`（Netty）等後綴形式。閘門必須能對這類字串判定 major 段。
- **版本字串完全無法解析**：依專案的 fail-fast 原則，不得靜默視為「無變動」而放行；必須標示為無法判定並讓建置失敗，訊息需帶上實際的版本字串。
- **依賴座標改名**（groupId 或 artifactId 變更）：會同時呈現為一項移除與一項新增。閘門不需自動識別兩者為同一依賴，但報告需讓人能看出這種配對關係。
- **基準線 tag 的排序**：`v1.10.0` 在語意化版本上晚於 `v1.9.0`，但字典序相反。基準線必須依語意化版本排序判定，而非字典序或 commit 時間。
- **基準線對應的 commit 已無法重建依賴圖**（例如當時的 toolchain 或建置設定已不適用）：閘門需有明確、不靜默的處理方式。
- **同一變更集使某依賴跨越多個 major 版本**（6.x → 8.x）：仍視為單一項阻擋性變更，但需完整呈現前後版本。
- **同一依賴同時存在多個版本線**（如 redis 1.3.0 的 Netty 4.1.125 與 4.2.12 並存）：任一版本線消失即為移除，須被偵測到。

## Requirements *(mandatory)*

### Functional Requirements

**依賴集合的判定**

- **FR-001**: 系統 MUST 針對每個已發布模組，判定其「會外溢給下游消費者」的依賴集合——即下游取用該 artifact 後會出現在其編譯或執行環境中的依賴，而非本專案內部建置與測試專用的依賴。
- **FR-002**: 系統 MUST 涵蓋 repo 內所有已發布模組；新增模組時 MUST NOT 需要修改閘門本身即自動納入保護範圍。

**基準線**

系統有兩種用途不同的比對基準，兩者並存且不互相取代：

- **FR-003**: 用於**阻擋**時（合併前的閘門），系統 MUST 以「本次變更集的起點狀態」作為基準線，回答「這次變更造成了什麼」。已於先前變更集中被攔截並核准過的差異 MUST NOT 重複阻擋——重複回報同一項只會產生雜訊，最終導致閘門被忽略。
- **FR-004**: 用於**發版揭露**時，系統 MUST 以該模組最近一次已發布的版本作為基準線，回答「自上次發布以來累積了什麼」。此基準線的判定 MUST 依語意化版本排序，MUST NOT 依字典序或 commit 時間。
- **FR-005**: 模組尚無可用基準線時，系統 MUST 跳過該模組的比對，MUST NOT 讓建置失敗，且 MUST 在報告中明確記錄跳過的模組與原因。

**差異偵測與分類**

- **FR-006**: 系統 MUST 偵測並分類三類差異：版本變動、依賴新增、依賴移除。
- **FR-007**: 版本變動 MUST 進一步分類為 major、minor、patch、版本後退。版本後退（新版本低於基準線版本）MUST 獨立成一類，不得併入上述任一類——基準線曾提供的 API 可能因後退而消失，風險等同 major。
- **FR-007a**: 基準線版本的 major 段為 0 時，minor 段前進 MUST 分類為 major。語意化版本規範明訂 0.y.z 為不穩定期，該區間的 minor 前進即可能破壞相容。
- **FR-008**: 系統 MUST 能對含發布後綴的版本字串（如 `6.8.2.RELEASE`、`4.1.136.Final`）判定其 major 段。
- **FR-009**: 版本字串無法判定 major 段時，系統 MUST 將其標示為「無法判定」並讓建置失敗，訊息 MUST 帶上實際的版本字串；MUST NOT 靜默視為無變動。

**閘門判定**

- **FR-010**: 系統 MUST 在偵測到 major 版本跳動、版本後退或依賴移除時讓建置失敗。
- **FR-011**: 系統 MUST NOT 因 minor 變動、patch 變動或依賴新增而讓建置失敗。
- **FR-012**: 系統 MUST 在單次執行中列出所有阻擋性變更，MUST NOT 在遇到第一項後即中止。
- **FR-013**: 失敗訊息 MUST 指出：模組名稱、依賴座標、基準線版本、當前版本、變更類別。

**核准途徑**

- **FR-014**: 維護者 MUST 能核准特定的破壞性變更，使其不再阻擋建置。
- **FR-015**: 核准 MUST 限定於特定的模組、依賴座標與版本區間，MUST NOT 為全域性的停用開關。
- **FR-016**: 核准 MUST 留下可事後查閱的紀錄，涵蓋核准了哪個模組的哪個依賴、哪個版本區間。
- **FR-017**: 已核准項目所對應的變更成為新基準線後，該核准 MUST NOT 繼續影響後續判定。

**報告**

- **FR-018**: 系統 MUST 產出人類可讀的依賴差異報告，涵蓋所有類別的變動，包含不阻擋建置的項目。
- **FR-019**: 報告 MUST 在建置成功與失敗兩種情況下皆產出。
- **FR-020**: 報告 MUST 區分阻擋性變動與資訊性變動。
- **FR-021**: 報告格式 MUST 能直接貼入 CHANGELOG 的「升級前必讀」段落與 GitHub Release notes 而無需重新排版。
- **FR-022**: 報告 MUST 以繁體中文呈現說明文字，與本專案既有文件一致。

**可用性**

- **FR-023**: 維護者 MUST 能在本地以單一指令重現 CI 的判定結果與報告。

### Key Entities

- **外溢依賴集合（Exposed Dependency Set）**：某模組某一版本會傳遞給下游消費者的依賴座標與其解析後版本的集合。是所有比對的基本單位。
- **基準線（Baseline）**：某模組最近一次已發布版本所對應的外溢依賴集合。
- **依賴差異（Dependency Delta）**：基準線與當前狀態之間的單一項差異，具備模組歸屬、依賴座標、前後版本、變更類別（major / minor / patch / 版本後退 / 新增 / 移除 / 無法判定）與阻擋性標記。
- **核准紀錄（Approval Record）**：對特定模組、依賴座標、版本區間的破壞性變更的明示核准，含核准理由。
- **閘門判定（Gate Verdict）**：一次執行的整體結果，為「通過」、「阻擋」或「跳過（無基準線）」，並持有該次執行的所有依賴差異。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 重現 2026-08-01 的情境（自有原始碼零變更、Spring Boot 4.0.6 → 4.1.0）時，閘門在合併前即阻擋，並點出 Lettuce 6.8.2.RELEASE → 7.5.2.RELEASE 的 major 跳動——該項當時直到發布後才由人工比對發現。同時，閘門**不得**列出 Netty 4.1.x 的移除：當時的人工揭露誤將 `dependencies` 輸出中的 requested 版本當成解析結果，實際的外溢依賴集合中並無此項（見本文件開頭的事後更正）。
- **SC-002**: 任何含未經核准之破壞性傳遞依賴變更的變更集，皆無法合併進正式分支。
- **SC-003**: 僅含 minor 或 patch 依賴更新的變更集，因本閘門而失敗的比率為 0%。
- **SC-004**: 撰寫發版揭露所需的依賴變更資訊 100% 可自報告取得，發版者不需自行比對依賴樹。
- **SC-005**: 閘門使單次 PR 檢查的總時長增加不超過 3 分鐘。
- **SC-006**: 新增第三個 starter 模組並完成首次發布後，該模組自動受閘門保護，過程中不需修改閘門本身的設定。
- **SC-007**: 維護者在本地執行單一指令，即可取得與 CI 完全一致的判定結果與報告。

## Assumptions

- **基準線來源**：沿用 repo 既有的 module-scoped tag 慣例（`<module>/v<version>`）作為「已發布版本」的認定依據，此慣例持續有效。
- **外溢範圍的認定**：以「下游消費者取得 published artifact 後可見的依賴」為準。本專案的測試依賴、建置工具依賴、以及以 `compileOnly` 引入的選用依賴（如 Actuator）不在保護範圍內。
- **破壞性的判定標準**：依語意化版本約定，major 版本跳動即視為潛在破壞性，不進一步分析下游是否「實際」使用到被破壞的 API。以精確度換取零漏報——寧可多攔一次由人核准，不可漏放一次。
- **依賴移除視為阻擋性**：下游可能正依賴該座標的存在（Netty 4.1.x 即為實例），故移除與 major 跳動同等對待。
- **依賴新增不視為阻擋性**：新增依賴不會使下游既有程式碼失效，僅列入報告。
- **觸發時機**：閘門在每次變更集的例行檢查中執行，而非僅在發版時執行——「合併前攔截」是本功能的核心訴求。
- **不採用 Gradle 內建 dependency locking**：它會鎖住所有依賴，而 Dependabot 對 Gradle lockfile 再生的支援不完整，將導致每支 bot PR 紅燈，違反 User Story 3。
- **不採用 japicmp**：它比對的是自有 artifact 的 binary API。在本案例中自有 API 完全未變，japicmp 會直接放行，無法攔截此類問題。
- **工具鏈輕量原則**：本 repo 刻意不使用 checkstyle / spotless 等工具，此閘門同樣不應引入沉重外掛或大量設定。
- **範圍邊界**：本功能只保護「已發布模組對下游的相容性」，不涵蓋安全漏洞掃描、授權合規檢查，亦不涵蓋自有原始碼的 API 相容性（後者未來若有需要為獨立議題）。
